# Как сдать лабораторную

## 1. Несколько слов, которые встретятся дальше

**Git** хранит историю изменений файлов на вашем компьютере. **GitLab** — сайт, на котором лежит серверная копия проекта и проходит проверка работ.

| Слово | Что это означает |
| --- | --- |
| Репозиторий | Папка с кодом и его историей. Внутри есть скрытая папка `.git`. |
| Клонирование (`clone`) | Первое скачивание репозитория вместе с историей. |
| Ветка (`branch`) | Отдельная линия работы. В `lab0` делаем нулевую лабораторную, в `lab1-0` — следующую. |
| Коммит (`commit`) | Сохранённая версия выбранных изменений с коротким пояснением. |
| `origin` | Имя серверного репозитория, которое Git создаёт при клонировании. |
| `push` | Отправка коммитов с компьютера на сервер. |
| `pull` | Получение изменений с сервера в текущую ветку. |
| Merge Request (MR) | Страница сдачи работы: предложение объединить вашу ветку с `master`, с обсуждением кода и результатами тестов. |
| CI / pipeline | Автоматическая сборка и проверки на сервере. Один запуск проверок называется pipeline. |

Сохранение файла в редакторе, создание коммита и отправка на сервер — **три разных действия**.

## 2. Подготовка

### Установите инструменты

Нужны Git, CMake и компилятор языка C. Редактор, например VSCode, сам по себе компилятор не устанавливает.

- [Скачать Git](https://git-scm.com/downloads/).
- [Подготовить CMake и компилятор для своей ОС](how_to_cmake.md#подготовка-инструментов).
- [Настроить редактор](how_to_ide.md).

Команды ниже вводятся в **терминале**. В Linux/macOS это Terminal, в Windows — PowerShell; для сборки через MSVC потребуется терминал разработчика, описанный в инструкции по сборке. В VSCode терминал открывается через **Terminal -> New Terminal**.

Копируйте по одной строке и выполняйте следующую после завершения предыдущей. Если команда закончилась ошибкой, сначала разберитесь с ней.

Проверьте Git:

```bash
git --version
```

В ответ должна появиться версия. Если команда не найдена, установите Git и заново откройте терминал.

### Укажите автора коммитов

Подставьте свои имя и почту:

```bash
git config --global user.name "Иван Иванов"
git config --global user.email "ivan.ivanov@example.com"
```

Эти данные будут видны в истории. Это подпись автора, а не вход в GitLab. Настройка `--global` действует для всех ваших репозиториев на этом компьютере.

### Подготовьте вход в GitLab

Откройте [GitLab ФИТ НГУ](https://gitlab.ccfit.nsu.ru/) и войдите в свою учётную запись. Убедитесь, что можете открыть свой студенческий проект.

В этой инструкции используем **HTTPS**. Если Git при клонировании или отправке попросит учётные данные, введите свой логин GitLab. Если пароль не принимается, используйте персональный токен:

1. В настройках своего профиля найдите **Access Tokens / Personal access tokens**. Название и расположение пункта зависят от версии GitLab.
2. Создайте токен, например с именем `study-laptop`, сроком действия на нужный период и правом **`write_repository`**: оно позволяет скачивать и отправлять код.
3. Скопируйте токен сразу после создания.
4. При запросе `Username` введите логин GitLab, а при запросе `Password` — токен. При вводе в терминале символы пароля могут не отображаться — это нормально.

Токен храните как пароль. Не вставляйте его в URL, исходники, коммиты или сообщения преподавателю. Подробнее: [токены доступа в GitLab](https://docs.gitlab.com/user/profile/personal_access_tokens/).

Если у вас уже работает доступ по SSH, можно скопировать SSH-адрес проекта: остальные команды Git останутся такими же. Для скачивания открытого проекта авторизация иногда не нужна, но для `push` нужны права на запись именно в ваш проект.

## 3. Скачайте свой репозиторий

1. В GitLab откройте проект **со своим логином** в группе своего потока.
2. Нажмите **Code / Clone** и скопируйте **Clone with HTTPS**.
3. Откройте терминал в папке, где хотите хранить учебные проекты.
4. Выполните `git clone`, подставив скопированный адрес.

**Пример:**

```bash
git clone https://gitlab.ccfit.nsu.ru/c_programming_autumn/26208/s.goncharova1/template.git
cd template
```

`git clone` создаёт папку `template`, а `cd template` переходит в неё. Клонировать заново перед каждой лабораторной не нужно.

**Все дальнейшие команды Git выполняйте из корня `template`** — папки, где одновременно видны `lab0`, `lab1-0`, `modules` и `.gitlab-ci.yml`:

```text
template/                 #  корень вашего репозитория
├── .git/                 #  история Git; эту папку не редактируем
├── .gitlab-ci.yml        #  настройки проверок на сервере
├── modules/              #  общие правила сборки
├── lab0/
│   ├── README.md         #  условие лабораторной
│   ├── CMakeLists.txt    #  описание сборки
│   ├── src/main.c        #  здесь начинаем писать решение
│   └── test/             #  готовые тестировщики
└── lab1-0/
```

Чтобы посмотреть текущую папку, в Linux/macOS или PowerShell выполните `pwd`, чтобы увидеть её содержимое — `ls`. Команда `cd ..` поднимается на один уровень вверх. Путь с пробелами заключайте в кавычки: `cd "путь к папке/template"`.

Проверьте подключение к нужному проекту:

```bash
git remote -v
git status
```

В адресе `origin` должен быть ваш проект. После свежего клонирования `git status` показывает ветку `master` и отсутствие изменений (`nothing to commit, working tree clean`).

## 4. Создайте ветку лабораторной

Начинайте новую лабораторную от актуальной `master`. Перед переключением проверьте `git status`: если есть несохранённые в коммит изменения предыдущей работы, сначала закончите их сохранение в соответствующей ветке.

Из корня `template`:

```bash
git status
git switch master
git pull --ff-only origin master
git switch -c lab0
git branch --show-current
```

Что произошло:

- `git switch master` выбрал основную ветку.
- `git pull --ff-only origin master` получил её обновления с сервера. Если Git не может просто обновить ветку, команда остановится; при такой ошибке обратитесь за помощью.
- `git switch -c lab0` создал ветку `lab0` и сразу переключил вас в неё.
- Последняя команда должна напечатать `lab0`.

**Имя ветки должно в точности совпадать с именем папки лабораторной.** Для `lab1-0/` создаём `lab1-0`, для `lab3-1/` — `lab3-1`. Имена вроде `Lab0`, `lab0-fix` или `ivan/lab0` не подходят: CI берёт имя ветки и ищет папку с таким же именем.

Создание ветки не создаёт новую папку на диске. Вы продолжаете работать в том же `template`, а Git хранит изменения отдельно от `master`.

Если ветка `lab0` уже существует и вы продолжаете работу над ней, используйте только:

```bash
git switch lab0
```

## 5. Напишите, соберите и проверьте программу

Откройте `lab0/README.md` и прочитайте условие. Решение пишите в `lab0/src/main.c`. Сохраняйте файлы в редакторе перед сборкой.

Далее пройдите [инструкцию по сборке и TestDriver](how_to_cmake.md). В ней есть команды для Linux, Windows и macOS, скачивание тестировщиков и разбор ошибок. Все команды сборки там также начинаются из корня `template`.

Например, для Linux/macOS сборка выглядит так:

```bash
cmake -S lab0 -B build/lab0 -DCMAKE_BUILD_TYPE=Release
cmake --build build/lab0
```

Первая команда готовит сборку, вторая создаёт исполняемую программу. Если у вас CMake 4.x и он сообщает о старой совместимости проекта, используйте вариант команды из раздела об ошибках в инструкции по сборке.

Готовый Linux-тестировщик запускается так **только на Linux**:

```bash
cd build/lab0
../../lab0/test/testlab0 ./lab0
cd ../..
```

На Windows нужен `.exe`, на macOS — тестировщик, собранный для macOS; соответствующие команды есть в инструкции. После каждого изменения кода снова выполняйте сборку и тесты: тестировщик проверяет исполняемый файл, а не текст в редакторе.

## 6. Сохраните решение в коммит

Вернитесь в корень `template`. Проверьте имя ветки и свои изменения:

```bash
git branch --show-current
git status
git diff
```

Должна быть выбрана `lab0`. В `git diff` строки с `+` добавлены, с `-` удалены. Если просмотр открылся на весь терминал, нажмите `q`, чтобы выйти. Новые файлы до `git add` видны в `git status` как `untracked`, но не в обычном `git diff`.

Выберите файлы, которые войдут в коммит:

```bash
git add lab0/src/main.c
git diff --cached
git commit -m "lab0: добавить перевод между системами счисления"
```

- `git add` подготавливает **текущее содержимое** файла к коммиту.
- `git diff --cached` показывает именно то, что будет сохранено.
- `git commit` сохраняет выбранные изменения локально и подписывает их текстом после `-m`.

Если после `git add` вы ещё раз исправили файл, повторите `git add` перед коммитом.

Если решение состоит из нескольких файлов, добавьте их тоже. Например, **только если создали эти файлы и изменили описание сборки**:

```bash
git add lab0/src/main.c lab0/src/convert.c lab0/src/convert.h lab0/CMakeLists.txt
```

В коммит должны попасть исходники и необходимые изменения сборки. Сборочные папки, исполняемые файлы, скачанный TestDriver и созданные тестами `in.txt`/`out.txt` отправлять не нужно. Папка `build/` уже исключена через `.gitignore`; явный список файлов в `git add` помогает проверить состав коммита.

Проверьте результат:

```bash
git status
git log -1 --oneline
```

Вторая команда покажет последний коммит и ваше сообщение. Если `git status` всё ещё показывает изменения решения, проверьте, не забыли ли вы добавить файл. За одну лабораторную можно делать сколько угодно осмысленных коммитов.

## 7. Отправьте ветку на сервер

Первый раз для ветки `lab0`:

```bash
git push -u origin lab0
```

Команда отправляет локальные коммиты в GitLab. Параметр `-u` запоминает, с какой серверной веткой связана ваша локальная ветка. При следующих отправках из неё достаточно `git push`.

Если Git запросит вход, используйте свои учётные данные из шага 2. После успешной отправки откройте проект в браузере, выберите ветку `lab0` и убедитесь, что видны ваш код и последний коммит.

CI запускается после отправки коммитов, ещё до создания MR. Отправка ветки сама по себе не означает, что работа сдана: теперь нужно открыть страницу проверки.

## 8. Откройте Merge Request

После `push` GitLab может показать ссылку или кнопку **Create merge request**. Если её нет:

1. Откройте **свой проект** в GitLab.
2. Перейдите в **Merge requests -> New merge request** (в некоторых версиях раздел находится внутри **Code**).
3. Выберите **Source branch** — `lab0`, **Target branch** — `master`. Обе ветки должны относиться к вашему студенческому проекту; если GitLab предлагает общий шаблон как целевой проект, выберите свой.
4. Нажмите **Compare branches and continue**.
5. Укажите понятный заголовок, например `lab0: перевод между системами счисления`. В описании кратко напишите, что сделано, какие тесты запускали и есть ли вопросы.
6. В поле **Assignee / Assignees** найдите `s.polokhin` и выберите **`@s.polokhin`**.
7. В поле **Reviewer / Reviewers** также найдите и выберите **`@s.polokhin`**.
8. Проверьте вкладку с изменениями: там должна быть ваша лабораторная, без случайных файлов других работ. Готовый к проверке MR не должен быть помечен **Draft**.
9. Нажмите **Create merge request**.

**Нужно заполнить оба поля:** Assignee — ответственный за MR, Reviewer — проверяющий код. Простое упоминание `@s.polokhin` в описании эти назначения не заменяет. Если полей не было в форме, найдите их справа в созданном MR и нажмите **Edit**. Если пользователь не находится, сообщите преподавателю ссылку на свой проект.

Названия кнопок могут немного отличаться в нашей версии GitLab. Справка: [создание MR](https://docs.gitlab.com/user/project/merge_requests/creating_merge_requests/) и [назначение Reviewer](https://docs.gitlab.com/user/project/merge_requests/reviews/).

### Проверьте CI

Откройте pipeline по значку проверки в MR или через **CI/CD -> Pipelines / Build -> Pipelines**. В текущем шаблоне за вашу ветку отвечает задание **`on_branch`**. Откройте его, чтобы увидеть журнал сборки и тестов.

- **Pending / Running** — проверка ждёт запуска или ещё идёт.
- **Passed** — этот запуск проверок завершился успешно.
- **Failed** — откройте журнал задания и найдите этап с ошибкой.

На сервере запускаются тестировщики из папки лабораторной `test/`. Помимо обычных тестов CI выполняет сборки с проверками памяти и неопределённого поведения, а также проверяет стиль через `cppcheck`. Поэтому локальное прохождение тестов ещё не гарантирует зелёный pipeline. [Подробнее об этапах CI](how_to_cmake.md#что-проверяет-ci).

Дождитесь результата **последнего отправленного коммита**. Зелёные тесты не заменяют проверку преподавателя: работа принимается после успешных автотестов и код-ревью. Объединение MR с `master` выполняет преподаватель.

## 9. Как дослать исправления

Если преподаватель оставил замечания или вы сами нашли ошибку, продолжайте в **той же ветке `lab0`**. Открытый MR обновится автоматически после отправки новых коммитов. Перед переключением проверьте, что рабочая папка чистая; изменения другой работы сначала сохраните в её ветке.

Из корня `template`:

```bash
git status
git switch lab0
git pull --ff-only
```

`pull` полезен, если вы работали с другого компьютера или редактировали файлы через сайт; здесь он выполняется после первого `push -u`.

Далее:

1. Исправьте код в редакторе и сохраните файлы.
2. **Заново соберите программу и запустите тесты** по инструкции для своей ОС.
3. Вернитесь в корень `template` и выполните:

```bash
git diff
git add lab0/src/main.c
git diff --cached
git commit -m "lab0: исправить проверку недопустимых цифр"
git push
```

Если исправляли другие файлы, добавьте их в `git add` тоже.

Откройте **существующий MR**: в нём появится новый коммит, изменится код и запустится новый pipeline. Ответьте на замечания коротко и по существу, например: «Исправил проверку цифр, тесты проходят». Если нужна повторная проверка, нажмите **Re-request a review**, когда такая кнопка доступна рядом с Reviewer, или оставьте комментарий с просьбой посмотреть исправления.

Для дополнений к открытому MR не нужно заново клонировать проект, создавать ветку `lab0-fix` или открывать ещё один MR. Если MR уже объединён с `master`, согласуйте дальнейшие исправления с преподавателем.

## 10. Как начать следующую лабораторную

Когда текущие изменения сохранены и отправлены, можно начинать следующую работу, даже если предыдущая ещё проверяется. Из корня `template`:

```bash
git status
git switch master
git pull --ff-only origin master
git switch -c lab1-0
```

Теперь работайте в `lab1-0/src/main.c`, собирайте `lab1-0`, используйте её тестировщик и отправляйте `git push -u origin lab1-0`. Для неё откройте отдельный MR: `lab1-0` -> `master`, снова с `@s.polokhin` в обоих полях.

Создавайте каждую новую ветку **из `master`**: так в MR следующей лабораторной не попадут ещё не принятые изменения предыдущей.

## Если что-то пошло не так

| Сообщение или ситуация | Что сделать |
| --- | --- |
| `not a git repository` | Вы вне репозитория. Перейдите через `cd` в папку `template`. |
| `destination path 'template' already exists` | Проверьте существующую папку. Если это уже ваш клон, перейдите в неё; повторное клонирование не требуется. |
| `a branch named 'lab0' already exists` | Для продолжения работы выполните `git switch lab0`, без `-c`. |
| `Author identity unknown` | Настройте `user.name` и `user.email` из шага 2. |
| `nothing to commit` | Сохраните файл в редакторе, проверьте `git status` и `git add`. Возможно, изменения уже закоммичены — посмотрите `git log -1 --oneline`. |
| `Everything up-to-date`, но на сайте старый код | Проверьте, создали ли вы коммит, какую ветку отправили и какую ветку смотрите в GitLab. |
| `Authentication failed` / `HTTP Basic: Access denied` | Проверьте логин и токен, срок его действия и право `write_repository`. Сохранённые старые учётные данные GitLab можно удалить в диспетчере учётных данных ОС и повторить вход. |
| `403` / `You are not allowed to push code` | Проверьте `git remote -v`: это должен быть ваш проект. Если адрес верный, обратитесь к преподавателю за проверкой прав. |
| `Could not resolve host` | Проверьте интернет и открывается ли GitLab в браузере. Это ошибка доступа к адресу сервера, а не текста программы. |
| `non-fast-forward` / `fetch first` при `push` | На сервере есть коммиты, которых нет у вас. В нужной ветке, после сохранения локальных изменений в коммит, выполните `git pull --ff-only`. Если он отказался — попросите помочь объединить истории; не используйте `push --force`. |
| `Your local changes ... would be overwritten` | Есть изменения, мешающие переключению. Проверьте `git status` и сохраните работу в правильной ветке. Если не уверены, покажите вывод преподавателю. |
| CI не находит папку лабораторной | Сравните `git branch --show-current` с точным именем папки: например, `lab1-0`. |
| MR пустой или показывает чужие лабораторные | Проверьте Source/Target и целевой проект. Источник — ветка своей лабораторной, цель — `master` своего проекта. |

Когда просите помощи, приложите команду, текст ошибки, вывод `git status` и ссылку на свой MR, если он уже есть. Пароли и токены не присылайте.

## Перед отправкой на проверку

- [ ] Работа находится в ветке с точным именем папки лабораторной.
- [ ] Код сохранён, программа заново собрана, локальные тесты запущены.
