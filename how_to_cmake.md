# Как собрать лабораторную и запустить TestDriver

Эта инструкция — часть [руководства по сдаче лабораторных](how_to_git.md). Здесь собираем и проверяем `lab0`; для другой работы заменяйте её имя в путях и командах.

**Начинайте из корня репозитория `template`**, где лежат папки `lab0`, `lab1-0` и `modules`. Блоки команд для разных ОС — альтернативы: выполняйте только свой вариант. После запуска программы или тестов возвращайтесь в корень командой `cd ../..`, как показано ниже.

## Подготовка инструментов

Для сборки нужны:

- **Компилятор C** — превращает `main.c` и другие исходники в исполняемую программу.
- **CMake** — читает `CMakeLists.txt` и подготавливает команды сборки.
- **Инструмент сборки**, например Make, NMake или MinGW Make, — выполняет эти команды. Мы вызываем его через `cmake --build`.

Для команд в этой инструкции используйте CMake 3.21 или новее. Проверка:

```bash
cmake --version
```

### Linux

В Ubuntu/Debian инструменты можно установить так:

```bash
sudo apt update
sudo apt install git build-essential cmake
```

Для других дистрибутивов установите Git, CMake, GCC или Clang и Make через свой менеджер пакетов. Проверьте `cc --version` и `make --version`.

### macOS

Установите инструменты командной строки Apple:

```bash
xcode-select --install
```

Завершите установку в появившемся окне. Если инструменты уже установлены, повторять её не нужно. Проверьте `cc --version`.

Установите [CMake](https://cmake.org/download/). Если используете приложение CMake, в меню **Tools -> How to Install For Command Line Use** есть инструкция, как сделать команду `cmake` доступной в терминале. Если у вас уже установлен Homebrew, можно выполнить `brew install cmake`.

### Windows

Выберите один вариант компилятора.

**MSVC:** установите [Build Tools for Visual Studio](https://visualstudio.microsoft.com/downloads/) с компонентом **Desktop development with C++ / Разработка классических приложений на C++**. Он включает и компилятор C. Установите [CMake](https://cmake.org/download/) с добавлением в `PATH`, если команда `cmake` ещё недоступна.

Откройте через меню «Пуск» **Developer PowerShell for VS** для установленной версии Visual Studio/Build Tools. В нём должны работать команды `cl` и `nmake`. Затем перейдите в свой `template`, например `cd "C:\study\template"`. Обычный терминал VSCode может не знать путей к MSVC. Подробнее: [терминал разработчика Microsoft](https://learn.microsoft.com/en-us/cpp/build/building-on-the-command-line).

**MinGW-w64:** если он уже настроен, например для вашей IDE, откройте терминал, где доступны `gcc --version`, `mingw32-make --version` и `cmake --version`, и используйте блок MinGW ниже.

Git-команды из основного руководства подходят для обоих вариантов.

## 1. Где писать код

Прочитайте `lab0/README.md`. Начальное решение находится в `lab0/src/main.c`.

В `lab0/CMakeLists.txt` уже описана сборка:

```cmake
project(lab0 C)
set(SRC src/main.c)
add_executable(${PROJECT_NAME} ${SRC})
```

`project(lab0 C)` задаёт имя программы, а `SRC` — список исходников. Если добавили `lab0/src/convert.c`, включите его в этот список:

```cmake
set(SRC
    src/main.c
    src/convert.c
)
```

Заголовок, например `convert.h` рядом с `main.c`, подключайте в коде через `#include "convert.h"`. Общие правила в `modules/` и подключение `include(common_lab)` оставьте в проекте: ими пользуется CI. Предупреждения компилятора в шаблоне считаются ошибками, поэтому их тоже нужно исправлять.

## 2. Соберите программу

Сначала сохраните файлы в редакторе. Из корня `template` выполните команды для своей ОС.

### Linux/macOS

```bash
cmake -S lab0 -B build/lab0 -DCMAKE_BUILD_TYPE=Release
cmake --build build/lab0
```

### Windows: MSVC в Developer PowerShell

```powershell
cmake -S lab0 -B build/lab0 -G "NMake Makefiles" -DCMAKE_BUILD_TYPE=Release
cmake --build build/lab0
```

### Windows: настроенный MinGW-w64

```powershell
cmake -S lab0 -B build/lab0 -G "MinGW Makefiles" -DCMAKE_BUILD_TYPE=Release
cmake --build build/lab0
```

Что означают параметры:

- `-S lab0` — взять описание сборки из папки `lab0`.
- `-B build/lab0` — складывать результаты в `build/lab0`; CMake создаст её сам.
- `Release` — сборка с оптимизациями для проверки, в том числе ограничений времени.
- `-G` — выбрать инструмент сборки. Для Windows мы явно выбрали варианты, которые кладут программу прямо в `build/lab0`.

После успешной сборки появится `build/lab0/lab0` на Linux/macOS или `build/lab0/lab0.exe` на Windows. Если сборка завершилась ошибкой, исправьте её: в папке может остаться старая программа от предыдущей успешной сборки.

После правок существующих исходников достаточно повторить:

```bash
cmake --build build/lab0
```

После добавления файлов в `CMakeLists.txt` повторите обе команды: настройку и сборку.

## 3. Проверьте один пример вручную

У `lab0` ввод — две строки. Например, для перевода из двоичной системы в четверичную:

```text
2 4
111.01
```

Запустите программу из папки сборки.

**Linux/macOS:**

```bash
cd build/lab0
./lab0
```

**Windows (PowerShell):**

```powershell
cd build/lab0
.\lab0.exe
```

Введите `2 4`, нажмите Enter, введите `111.01` и снова Enter. Число в результате должно быть `13.1`; по условию возможны завершающие нули дробной части. Если программа читает до конца ввода, в Linux/macOS нажмите `Ctrl+D`, в Windows — `Ctrl+Z`, затем Enter. Зависшую программу можно прервать `Ctrl+C`.

После завершения программы вернитесь в корень:

```bash
cd ../..
```

Не выводите подсказки вроде «Введите число», если их нет в требуемом формате ответа. При работе с файлами используйте имена из условия лабораторной, например `in.txt` и `out.txt`, без абсолютных путей к своему компьютеру.

## 4. Где взять тестировщик

**TestDriver** — отдельная программа: она подготавливает входные данные, запускает ваше решение и проверяет его ответ.

В студенческом шаблоне уже есть готовые файлы:

| ОС | Файл для `lab0` |
| --- | --- |
| Linux x86-64 | `lab0/test/testlab0` |
| Windows | `lab0/test/testlab0.exe` |
| macOS | Нужно собрать из исходников, как показано ниже. Linux-файл на macOS не запускается. |

**Когда вы выполнили `git clone` своего проекта, эти готовые тестировщики уже скачались вместе с ним.** На Linux x86-64 и Windows начните с них: именно файлы из `lab0/test/` использует CI проекта.

Исходники опубликованы в [репозитории TestDriver](https://github.com/Evgueni-Petrov-aka-espetrov/TestDriver). Если требуется скачать их отдельно, например для macOS, из корня `template` выполните:

```bash
git clone https://github.com/Evgueni-Petrov-aka-espetrov/TestDriver.git ../TestDriver
```

Получатся соседние папки:

```text
study/
├── template/       ← ваш код и история сдачи
└── TestDriver/     ← исходники тестировщиков
```

Скачивание TestDriver нужно выполнить один раз. Если эта папка уже есть, используйте её. В браузере также можно выбрать **Code -> Download ZIP** и распаковать архив рядом с `template`, переименовав извлечённую папку в `TestDriver`.

**Версии могут различаться:** свежие исходники GitHub могут быть новее готовых файлов в студенческом проекте. Для окончательной проверки сдачи смотрим CI, использующий тестировщик из вашего репозитория.

### macOS: соберите тестировщик для `lab0`

После скачивания TestDriver выполните **из корня `template`**:

```bash
mkdir -p ../TestDriver/build
cc -std=gnu11 -O2 ../TestDriver/testDriver.c ../TestDriver/testlab0.c -lm -o ../TestDriver/build/testlab0
```

Эта команда собирает тестировщик из общего `testDriver.c` и тестов `testlab0.c`. Решение студента она не собирает — это отдельный шаг 2. Готовый тестировщик будет лежать в `../TestDriver/build/testlab0`.

В проверенной версии CMake-файла TestDriver задан `-static`, который мешает обычной сборке на macOS. Поэтому здесь собираем два исходника напрямую через `cc`. Такая же команда подходит для Linux с GCC/Clang, например если готовый Linux-файл не подходит архитектуре компьютера.

Для `lab1-0` замените `testlab0.c` и имя результата на `testlab1-0.c` и `testlab1-0`. У `lab3-1` используются тесты из `testlab3-0.c`, у `lab8-1` — из `testlab8-0.c`: в TestDriver эти пары используют общий тестировщик. Например:

```bash
cc -std=gnu11 -O2 ../TestDriver/testDriver.c ../TestDriver/testlab3-0.c -lm -o ../TestDriver/build/testlab3-1
```

## 5. Запустите автоматические тесты

Тестировщику обязательно нужно передать **путь к собранной программе**. Запуск одного `testlab0` без аргумента только покажет справку.

Тестировщик создаёт и перезаписывает `in.txt` и `out.txt` в **текущей папке**. Поэтому запускаем его из `build/lab0`, где лежит собранная программа. Не храните в этой папке единственную копию своих ручных тестов.

### Linux x86-64: тестировщик из шаблона

Из корня `template`:

```bash
cd build/lab0
../../lab0/test/testlab0 ./lab0
cd ../..
```

### Windows: тестировщик из шаблона

После сборки одним из двух вариантов выше, из корня `template` в PowerShell:

```powershell
cd build/lab0
..\..\lab0\test\testlab0.exe .\lab0.exe
cd ../..
```

Если IDE собрала программу в другой каталог, например `build/lab0/Release`, эти пути будут другими. Для команд в инструкции используйте сборку через NMake или MinGW, указанную выше.

### macOS (или Linux): самостоятельно собранный TestDriver

Из корня `template`:

```bash
cd build/lab0
../../../TestDriver/build/testlab0 ./lab0
cd ../..
```

Здесь `../../../TestDriver` поднимается из `template/build/lab0` в папку, общую для `template` и `TestDriver`, и заходит в TestDriver. Два пути в команде означают: **какую программу-тестировщик запустить** и **какое решение проверить**.

### Как понять результат

При полном успехе TestDriver пишет `passed all tests`. При ошибке он обычно останавливается на первом неудачном тесте. Например, пустой `main.c` из шаблона собирается, но тестировщик сообщает `no output -- FAILED`: программа не напечатала ответ.

После неудачного запуска:

1. Прочитайте сообщение: неверный ответ, отсутствие вывода, превышение лимита или аварийное завершение.
2. Посмотрите `build/lab0/in.txt` — вход последнего теста, и `build/lab0/out.txt` — вывод вашей программы, если он успел появиться. Ожидаемый ответ тестировщик не обязан сохранять в отдельный файл.
3. Исправьте исходники и сохраните их.
4. Выполните `cmake --build build/lab0` из корня `template`.
5. Повторите запуск тестировщика для своей ОС.

Сами тесты, настройки CI и лимиты ради прохождения проверки не меняем: исправляем решение.

### Дополнительно: запуск через CTest

На Linux x86-64 и Windows после описанной выше сборки можно попросить CMake запустить тестировщик из папки `lab0/test/`:

```bash
cd build/lab0
ctest --output-on-failure
cd ../..
```

CTest — оболочка для запуска того же тестировщика; сам программу он не пересобирает. На macOS этот вариант в исходном шаблоне укажет на готовый Linux-файл и не сработает. Используйте прямой запуск самостоятельно собранного TestDriver из предыдущего раздела.

## Что проверяет CI

После `git push` сервер берёт имя ветки, собирает соответствующую лабораторную и запускает проверки из `.gitlab-ci.yml`:

| Этап | Что проверяет |
| --- | --- |
| Release с `UNLIMITED=ON` | Тесты с увеличенными лимитами: 60 секунд и 1 ГиБ. Несмотря на название, лимиты здесь не бесконечные. |
| Release с `UNLIMITED=OFF` | Те же тесты с обычными лимитами тестировщика для лабораторной. |
| AddressSanitizer (ASAN) | Тесты с обнаружением ошибок памяти, например выхода за границы массива. |
| UndefinedBehaviorSanitizer (в шаблоне `ENABLE_USAN`) | Тесты с проверкой неопределённого поведения, например некоторых видов переполнения и некорректных операций. |
| `cppcheck` | Статический анализ исходников: предупреждения о возможных ошибках и стиле. |

Обычный локальный запуск TestDriver покрывает тесты, но не все эти дополнительные проверки. Возможны и различия ОС, компилятора и версии тестировщика. Если локально всё проходит, а pipeline красный, откройте журнал задания `on_branch` и найдите **какой именно этап** завершился ошибкой.

## Частые проблемы со сборкой и тестами

### CMake пишет `Compatibility with CMake < 3.5 has been removed`

Это проблема совместимости нового CMake со старым описанием сборки. Для CMake 4.x повторите настройку с дополнительным параметром, сохранив `-G`, если он был нужен на Windows:

```bash
cmake -S lab0 -B build/lab0 -DCMAKE_BUILD_TYPE=Release -DCMAKE_POLICY_VERSION_MINIMUM=3.5
cmake --build build/lab0
```

Параметр задаёт режим совместимости локально, без правок учебного `CMakeLists.txt`. Предупреждение `CMake Deprecation Warning` само по себе не означает провал сборки: смотрите, завершилась ли команда успешно.

### `C compiler ... is not able to compile` / `CMAKE_C_COMPILER` / `nmake` не найден

Проверьте установку компилятора и инструмента сборки. На Windows с MSVC откройте именно Developer PowerShell. Закройте и заново откройте терминал после установки инструментов.

### CMake сообщает, что выбранный генератор не совпадает с предыдущим

Вы использовали для одной папки сборки разные инструменты, например Visual Studio и MinGW. Выберите один вариант. В проводнике удалите **только созданную папку `template/build/lab0`** и повторите настройку и сборку. Исходники в `template/lab0` должны остаться.

### `undefined reference` / `unresolved external symbol`

Если ошибка возникла после разделения решения на файлы, проверьте, добавили ли вы новый `.c` в `set(SRC ...)` в `lab0/CMakeLists.txt`. Подключение `.h` через `#include` само по себе не добавляет реализацию функции в сборку.

### `No such file`, программа не найдена или не запускается

Проверьте текущую папку, успешность последней сборки и имя файла. На Windows нужен `.exe`. Если использовали свою сборку через IDE, найдите фактическое расположение программы или повторите сборку из этой инструкции.

### `Permission denied` при запуске Linux-тестировщика

Из корня `template` выдайте файлу разрешение на запуск:

```bash
chmod +x lab0/test/testlab0
```

Затем повторите запуск из `build/lab0`. При обычном клонировании шаблона разрешение уже выставлено.

### `Exec format error` / `cannot execute binary file`

Тестировщик собран для другой ОС или архитектуры. На macOS и Linux ARM соберите его из исходников по разделу 4.

### Тесты «не замечают» исправления

Сохраните исходники, заново выполните `cmake --build build/lab0` и проверьте, что TestDriver получает путь именно к этой программе. Он не читает ваш `main.c` и не запускает компилятор автоматически.

После локальной проверки вернитесь к [созданию коммита и отправке работы](how_to_git.md#6-сохраните-решение-в-коммит).
