# Целые числа и биты

{% include course-context.html %}

Число в программе имеет сразу два описания: математическое значение и набор
битов, которым это значение представлено. Начнём с позиционной записи,
затем разберём диапазоны типов, операции и просмотр байтов объекта.

## Из битов получается число

У десятичного числа каждая позиция имеет свой вес: единицы, десятки, сотни.
У двоичного веса такие: 1, 2, 4, 8, 16 и далее степени двойки.

```text
Биты:       0   0   0   0   1   1   0   1
Вес:      128  64  32  16   8   4   2   1

00001101₂ = 8 + 4 + 1 = 13₁₀
```

В восьми битах есть 256 различных комбинаций. Если все они обозначают
неотрицательные целые, можно представить числа от 0 до 255.
Для `N` битов значения диапазона — **от 0 до 2^N − 1**.

У каждого бита два варианта. Для двух битов вариантов `2 × 2 = 4`,
для трёх — `2 × 2 × 2 = 8`, для `N` — `2ᴺ`. Ноль занимает одну комбинацию,
поэтому максимальное неотрицательное значение на единицу меньше числа комбинаций.

Обратный перевод целого числа удобно делать делением на 2. Остаток
показывает младший бит: чётное число заканчивается на 0, нечётное — на 1.
После удаления младшего бита остаётся частное.

| Делимое | Частное при делении на 2 | Остаток |
| --- | ---: | ---: |
| 13 | 6 | 1 |
| 6 | 3 | 0 |
| 3 | 1 | 1 |
| 1 | 0 | 1 |

Остатки получены от младшего разряда к старшему. Читаем их снизу вверх:
`1101`. Сумма весов `8 + 4 + 1` возвращает исходное 13.

В C17 двоичная запись `0b1101` не является стандартным синтаксисом
(но некоторые компиляторы принимают её как расширение). Можно использовать
десятичную или шестнадцатеричную запись:

```c
unsigned int first = 13;
unsigned int second = 0x0D;
printf("%u %u\n", first, second); // 13 13
```

Одна шестнадцатеричная цифра обозначает четыре бита. Поэтому `0xD` — это
`1101`, а `0xFF` — `11111111`. Такая запись удобна, когда интересуют
конкретные группы битов.

### Сколько битов в типе C?

`int` далеко не всегда занимает четыре байта. Это зависит от того, на какой архитектуре запускается программа и как она компилировалась. Настоящий размер типа можно узнать в самой программе:

```c
#include <limits.h>
#include <stdio.h>

// Внутри main:
printf("char bits: %d\n", CHAR_BIT);
printf("int bytes: %zu\n", sizeof(int));
printf("int range: %d .. %d\n", INT_MIN, INT_MAX);
printf("unsigned int max: %u\n", UINT_MAX);
```

`sizeof` измеряет размер в **байтах C**. Один такой байт содержит `CHAR_BIT`
битов; на обычных современных компьютерах это 8, но язык не требует ровно 8.
Всегда выполняется `sizeof(char) == 1`. У некоторых целых типов возможны
биты заполнения, поэтому размер объекта в битах не всегда равен числу
битов, участвующих в представлении значения.

Если нужен тип ровно из 32 битов, смотрят на `uint32_t` и `int32_t`
из `<stdint.h>`. Эти типы предоставляются только тогда, когда реализация
может обеспечить нужное представление без битов заполнения.
Для переносимого вывода чисел этих типов используют макросы из `<inttypes.h>`:

```c
#include <stdint.h>
#include <inttypes.h>

uint32_t value = UINT32_C(4000000000);
printf("%" PRIu32 "\n", value); // 4000000000
```

Спецификатор должен соответствовать типу аргумента: `%d` — `int`, `%lu` —
`unsigned long`. За ними не закреплены размеры в четыре и восемь байтов.
Макрос `PRIu32` выбирает формат для того типа, которым реализация представляет `uint32_t`.

Пока достаточно понимать макрос как имя, которое до компиляции заменяется
другим текстом. Например, при замене `PRIu32` на `"u"` запись
`"%" PRIu32 "\n"` становится тремя соседними строковыми литералами:
`"%" "u" "\n"`. C объединяет их в одну строку `"%u\n"`.
На реализации с другим базовым типом подстановка будет другой.
`UINT32_C(...)` аналогично помогает получить целочисленную константу
нужной категории; это не вызов функции при выполнении.

## Беззнаковые целые: арифметика по кругу

У беззнакового типа нет отрицательных значений. Если результат операции
не помещается, он приводится по модулю числа представимых значений:

```c
unsigned int value = UINT_MAX;
value += 1u;
printf("%u\n", value); // 0

value = 0u;
value -= 1u;
printf("%u\n", value); // UINT_MAX, например 4294967295
```

Для восьми битов это легко увидеть на бумаге:

```text
  11111111  (255)
+ 00000001  (1)
----------
1 00000000  (256)
  └──────┘
Остаются младшие восемь битов: 0.
```

Здесь "возврат к нулю" — определённое поведение языка, а не случайность
конкретного процессора. Но результат всё равно может быть ошибкой алгоритма:
например, отрицательное математическое значение остатка превратится
в огромное положительное число.

Узкие целые типы сначала могут продвигаться до `int`. Например, для
`unsigned char` на обычной платформе сумма вычисляется как `int`, а затем
приводится при присваивании обратно. Поэтому в примере выше использован
именно `unsigned int`: не нужно путать тип хранения и тип вычисления.

Например, на платформе с восьмибитным `unsigned char` и обычным `int`
выражение `small + 1` при `small == 255` даёт `int` со значением `256`.
Если присвоить его обратно восьмибитному `unsigned char`, преобразование
даст 0. Но если сохранить в `int`, останется 256. Поэтому недостаточно
посмотреть на тип переменной слева: нужно отдельно понять тип операции
и преобразование при записи результата.

## Отрицательные числа: дополнительный код

Как разделить те же комбинации битов между положительными и отрицательными
значениями? На современных платформах обычно используется **дополнительный
код**, или two's complement.

Для восьми битов диапазон такого знакового типа — от −128 до 127.
Можно считать, что вес старшего бита равен −128, а остальные веса
положительны:

```text
Биты:       1   1   1   1   1   1   0   1
Вес:     -128  64  32  16   8   4   2   1

11111101₂ = -128 + 64 + 32 + 16 + 8 + 4 + 1 = -3
```

Другой способ получить представление −3: взять представление 3,
инвертировать все биты и прибавить единицу, оставив восемь битов:

```text
 3: 00000011
    11111100  <- инвертировали
-3: 11111101  <- прибавили 1
```

Откуда взялось правило «инвертировать и прибавить один»? Все единицы
в восьми битах означают 255. Инверсия записи числа 3 даёт `255 − 3 = 252`.
Прибавление единицы даёт `256 − 3 = 253`. Такой набор битов при сложении
с записью 3 даёт 256 — после отбрасывания девятого бита остаётся ноль.
Вообще представление `−x` получается как `2ᴺ − x` в `N` битах.
Поэтому сложение битовых записей согласуется с привычным сложением значений,
пока математический результат помещается в знаковый диапазон.

Старший бит указывает на отрицательное значение, но остальные биты
**не хранят просто модуль числа**. `10000011` в дополнительном коде — это
−125, а не −3.

Для `N` битов диапазон — **от −2^(N−1) до 2^(N−1) − 1**.
Отрицательных значений на одно больше: для 32-битного `int` это
−2147483648 ... 2147483647. Поэтому положительный аналог `INT_MIN`
в таком `int` не помещается.

Важная граница переносимости: **C17 допускает и другие представления
обычных знаковых целых**. Далее, когда обсуждаем конкретные знаковые биты,
предполагаем дополнительный код. Если реализация предоставляет `int32_t`,
для него C17 требует именно дополнительный код без заполнения.

### Дополнительный код не разрешает знаковое переполнение

```c
int value = INT_MAX;
value += 1; // Неопределённое поведение.
```

Даже если процессор при обычном сложении оставляет младшие биты, язык
не обещает здесь получить `INT_MIN`. Компилятор вправе оптимизировать код
исходя из того, что знакового переполнения в корректной программе нет.
См. [GNU: Integer Overflow](https://www.gnu.org/software/c-intro-and-ref/manual/html_node/Integer-Overflow.html).

Проверять переполнение нужно **до** операции. Например, для прибавления единицы:

```c
if (value < INT_MAX) {
    ++value;
} else {
    puts("Cannot increment");
}
```

Та же осторожность нужна с `-INT_MIN`, `abs(INT_MIN)` и `INT_MIN / -1`
на платформе с дополнительным кодом: положительный результат не помещается.

В предыдущем фрагменте `puts` из `<stdio.h>` выводит строку и добавляет перевод
строки; поэтому внутри её аргумента нет `\n`. `abs` из `<stdlib.h>` вычисляет
целочисленный модуль, но его результат также обязан помещаться в `int`.

## Побитовые операции и смешение типов

Операторы `&`, `|`, `^` и `~` работают с битами: И, ИЛИ, исключающее ИЛИ
и инверсия. Они отличаются от логических `&&`, `||` и `!`.

```c
unsigned int flags = 0u;
unsigned int mask = 1u << 3; // 00001000: бит с номером 3, считая от нуля.

flags |= mask;              // Установить бит.
printf("%d\n", (flags & mask) != 0u); // 1: проверить бит.
flags &= ~mask;             // Сбросить бит.
flags ^= mask;              // Переключить бит.
```

Пусть исходно `flags == 5`, то есть младшие биты равны `0101`,
а маска `1u << 3` имеет вид `1000`. У побитового ИЛИ каждая позиция
рассматривается отдельно:

```text
  0101   исходные флаги
| 1000   маска
------
  1101   нужный бит установлен, остальные сохранены
```

Для проверки используем И: `1101 & 1000` даёт `1000`, ненулевой результат.
Для сброса нужны единицы во всех позициях, кроме выбранной: такую маску
даёт `~mask`. Тогда `1101 & ...0111` возвращает `0101`.
Многоточие важно: `~` инвертирует все биты продвинутого операнда,
а не только четыре позиции, которые мы нарисовали.

Для масок удобны беззнаковые типы. Сдвиг на отрицательное число позиций
или на число, не меньшее ширины продвинутого левого операнда, недопустим.
Левый сдвиг отрицательного знакового значения имеет неопределённое поведение;
правый сдвиг отрицательного в C17 зависит от реализации. Даже с положительным
знаковым значением левый сдвиг требует проверки представимости результата.

Ещё одна ловушка — сравнение знакового и беззнакового:

```c
int debt = -1;
unsigned int count = 1u;

// debt < count даст ложь.
```

При таком сочетании типов `debt` преобразуется в `unsigned int` и становится
`UINT_MAX`. Сравнение фактически проверяет `UINT_MAX < 1u`.
Это правило преобразования типов, а не изменение исходного `debt`.

Если отрицательный `debt` действительно должен считаться меньшим любого
`count`, проверку можно записать явно:

```c
int isLess = debt < 0 || (unsigned int)debt < count;
```

Приведение выполняется только после того, как отрицательные значения
обработаны отдельно. Приведение "лишь бы убрать предупреждение" может скрыть ошибку.

## Число и порядок байтов — разные вещи

Возьмём 32-битное беззнаковое число `0x12345678`. Его старший байт — `0x12`,
младший — `0x78`. В памяти байты могут располагаться в разном порядке:

```text
Адреса растут слева направо.

little-endian: 78 56 34 12
big-endian:    12 34 56 78
```

Значение числа в обоих случаях одинаково. Порядок становится важен,
когда мы рассматриваем память как байты, читаем файл или передаём данные по сети.
Именно поэтому `pack` из [материала о структурах](records.md) не задаёт
полный формат данных.

Посмотреть представление объекта можно через `unsigned char*`:

```c
void PrintBytes(const void* object, size_t size) {
    const unsigned char* bytes = object;
    for (size_t i = 0; i < size; ++i) {
        printf("%02X%s", (unsigned int)bytes[i],
               i + 1 == size ? "\n" : " ");
    }
}
```

Вызывать, например, так: `PrintBytes(&value, sizeof(value));`.
Доступ к байтам представления через символьный тип разрешён.
Это тот же приём, который использовался в универсальном `swap`, только здесь
байты читаются через `const unsigned char*` и не изменяются.
В `%02X` `X` задаёт шестнадцатеричный вывод, `2` — минимальную ширину,
`0` — дополнение нулями. Приведение к `unsigned int` согласует тип с форматом.
Рабочая программа для платформы с 8-битным байтом: [numberBits.c]({{ '/materials/examples/numberBits.c' | relative_url }}).

В этом исходнике `_Static_assert(CHAR_BIT == 8, ...)` проверяет условие
**при компиляции** и останавливает сборку на неподходящей платформе.
Так предположение о восьмибитном байте становится явным, а не теряется в тексте.

## Одна запись, два значения

`11111110` означает 254 для восьмибитного беззнакового значения и −2
для восьмибитного значения в дополнительном коде. Биты совпадают,
но способ интерпретации различается. При этом правила знакового переполнения
задаются языком отдельно от представления: `INT_MAX + 1` не становится допустимым.
