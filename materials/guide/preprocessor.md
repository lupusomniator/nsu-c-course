# Препроцессор и макросы

{% include course-context.html %}

Директивы `#include` уже участвовали в многофайловом примере. Теперь проследим
другие преобразования исходного текста: от простой подстановки до составных
макросов. Во всех примерах будем явно записывать код после раскрытия.

## Что делает препроцессор

Упрощённо путь программы выглядит так:

```text
.c и заголовки -> препроцессор -> компилятор -> объектные файлы -> компоновщик
```

Препроцессор обрабатывает `#include`, `#define` и условную компиляцию.
Макрос — правило подстановки токенов, то есть элементов исходного кода:
имён, чисел, знаков операций. Это не функция, вызываемая во время исполнения.

```c
#define BUFFER_SIZE 64

char buffer[BUFFER_SIZE]; // После подстановки: char buffer[64];
```

У макроса нет собственного типа и адреса. Тип будет у выражения, которое
получится после раскрытия. В определение не ставят `=` и завершающий `;`:
они тоже стали бы частью подстановки.

```c
#define BAD_SIZE 64;     // Ошибка замысла: char buffer[BAD_SIZE] даст [64;].
#define COURSE_NAME "C"
```

Имена внутри строк не раскрываются: `"BUFFER_SIZE"` остаётся этой строкой.
Определение действует с места `#define` до `#undef` или конца единицы
трансляции, включая подключённые в неё заголовки. Фигурные скобки функции
не ограничивают область действия макроса. Поэтому им дают заметные имена
в `UPPER_SNAKE_CASE`, а публичным макросам — ещё и префикс проекта.

### Макрос, `enum` или `const`?

| Задача | Обычно подходит |
| --- | --- |
| Целая константа для размера или `case` | `enum { BUFFER_SIZE = 64 };` |
| Типизированный объект, который нельзя изменять | `const double scale = 0.5;` |
| Настройка для `#if` или из командной строки сборки | `#define FEATURE_ENABLED 1` |
| Вычисление над значениями | Функция, при необходимости `static inline` |

В C17 объект `const int n = 64;` не является целочисленным константным
выражением. Например, он не подходит для метки `case`; локальный массив
с таким размером будет VLA, если реализация поддерживает VLA.
`enum` удобен для небольших целых констант, представимых типом `int`.

## Макрос с параметрами: сначала раскройте его

В **определении** между именем функционального макроса и `(` не должно быть пробела:

```c
#define SQUARE_BAD(x) x * x
```

Подстановка не вычисляет аргумент заранее:

```c
SQUARE_BAD(2 + 3)
// Превращается в: 2 + 3 * 2 + 3
// Получается 11.
```

Первое исправление — скобки вокруг каждого использования аргумента:

```c
#define SQUARE_HALF(x) (x) * (x)

100 / SQUARE_HALF(5)
// 100 / (5) * (5) -> 100, а не 4.
```

Нужны также скобки вокруг всего результата:

```c
#define SQUARE(x) ((x) * (x))
```

Для арифметического макроса правило такое: **заключайте в скобки каждый
аргумент и всё выражение целиком**. Это исправляет приоритет операций,
но не следующую проблему.

## Аргумент может вычисляться несколько раз

```c
#define MIN(a, b) (((a) < (b)) ? (a) : (b))
```

Сначала вычисляется сравнение, затем — одна выбранная ветвь. Значит,
выбранный аргумент вычислится повторно:

В условном выражении `условие ? первое : второе` вычисляется только одна
выбранная ветвь. Постфиксное `value++` отдаёт старое значение и увеличивает
сам объект; префиксное `++value` даёт уже увеличенное значение.
Например, при `value == 3` отдельная инструкция `int old = value++;`
оставит `old == 3`, `value == 4`.

```c
int value = 3;
int result = MIN(value++, 10);
// Сравнение: 3 < 10, затем value становится 4.
// Выбрана первая ветвь: она отдаёт 4, затем value становится 5.
// Итого result == 4, value == 5.
```

После подстановки выражение имеет вид
`((value++) < (10) ? (value++) : (10))`.
Здесь два вхождения `value++` стоят в разных частях управления:

| Этап | Значение выражения | `value` после этапа |
| --- | --- | ---: |
| Левый операнд сравнения | 3 | 4 |
| Проверка `3 < 10` | Истина | 4 |
| Выбранная первая ветвь | 4 | 5 |
| Запись результата в `result` | 4 | 5 |

Таким образом, побочный эффект — изменение `value` — произошёл дважды.
Скобки меняют группировку выражения, но не число его вхождений.

Этот конкретный пример имеет определённое поведение: вычисление условия
`?:` завершено до вычисления выбранной ветви. Но результат всё равно
не похож на минимум первоначальных значений 3 и 10.

А `SQUARE(value++)` даёт `((value++) * (value++))`: два неупорядоченных
изменения одного объекта — **неопределённое поведение**. Предсказывать вывод
или проверять его многократными запусками бессмысленно.

Проблема касается и вызовов: `MIN(ReadValue(), 10)` может прочитать значение
дважды. Скобки не исправляют повторное вычисление.

Для вычислений лучше функция:

```c
static inline int MinInt(int left, int right) {
    return left < right ? left : right;
}
```

`MinInt(value++, 10)` вычислит каждый аргумент один раз. Но порядок вычисления
аргументов функции в C не задан: `MinInt(value++, value++)` также недопустим.
`inline` не гарантирует встраивание и не нужен для правильности программы;
`static inline` удобно для короткой реализации в заголовке.

`static` здесь имеет уже знакомый смысл внутреннего связывания:
каждая единица трансляции получает собственную функцию. `inline`
сигнализирует о возможности подстановки тела при оптимизации, но выбор
остаётся за компилятором. Для обычной функции в одном `.c` достаточно
`int MinInt(...)`; ключевые слова не исправляют повторные вычисления сами по себе.

Рабочие примеры без неопределённого поведения: [macros.c]({{ '/materials/examples/macros.c' | relative_url }}).

## `#`: получить текст аргумента

Обычная функция получает уже вычисленные значения. Если ей передали
`count + 1`, она видит число, но не знает, как именно было написано выражение.
У макроса есть доступ к написанию аргумента:

```c
#define TEXT(x) #x

// TEXT(count + 1) раскрывается в "count + 1".
```

`#` перед параметром превращает его в строковый литерал. Например,
`printf("%s\n", TEXT(count + 1));` напечатает `count + 1`, даже если
переменная `count` вообще не объявлена: выражение не вычисляется.

Соседние строковые литералы C объединяет. Поэтому после раскрытия
`#x " = "` получается, например, `"count + 1" " = "`, а затем одна строка
`"count + 1 = "`. Это позволяет вывести рядом написание выражения и его значение.

## Несколько инструкций: `do { ... } while (0)`

Пусть нужен макрос для вывода целочисленного выражения вместе с его именем.
В первой версии две инструкции:

```c
// Намеренно неудачная версия:
#define PRINT_INT_BAD(x) printf(#x " = "); printf("%d\n", (x))
```

Такой макрос не ведёт себя как одна инструкция. Например, следующий
**намеренно плохой стиль без фигурных скобок** сломается при раскрытии:

```c
if (debug)
    PRINT_INT_BAD(count);
else
    puts("quiet");
```

После подстановки между `if` и `else` окажется отдельный `printf`.
Просто `{ ... }` внутри макроса тоже недостаточно: привычная точка с запятой
после его вызова создаст лишнюю инструкцию перед `else`.

Это видно по раскрытому коду. Для первой версии получаем:

```c
// Намеренно ошибочный результат раскрытия.
if (debug)
    printf("count = ");
printf("%d\n", count);
else
    puts("quiet");
```

Под `if` попала только первая инструкция, а `else` уже не может связаться
с ним через отдельный `printf`. Версия с одним блоком даёт другой дефект:

```c
// Также намеренно ошибочный результат раскрытия.
if (debug) { printf("count = "); printf("%d\n", count); };
else puts("quiet");
```

После `}` стоит лишняя пустая инструкция `;`, тоже отделяющая `else` от `if`.

Стандартный приём — обернуть тело в один оператор `do`:

```c
#define PRINT_INT(x) do { \
    printf(#x " = "); \
    printf("%d\n", (x)); \
} while (0)
```

Вызов пишется с точкой с запятой: `PRINT_INT(count);`. Тело выполнится один
раз, затем ложное условие завершит цикл. После `while (0)` в **определении**
точку с запятой не ставят: её добавляет вызывающий код.
`\` продолжает директиву на следующей строке; после него не должно быть пробелов.

Теперь раскрытие имеет вид `if (debug) do { ... } while (0); else ...`.
Точка с запятой принадлежит синтаксису `do ... while`, поэтому между
целой инструкцией цикла и `else` ничего лишнего нет. При
`PRINT_INT(count + 1)` и `count == 7` вывод будет `count + 1 = 8`.
Для `%d` выражение должно иметь подходящий тип `int` после продвижений;
универсального форматирования любых типов этот макрос не добавляет.

Сам приём не устраняет повторное вычисление аргументов и конфликты имён
локальных переменных. Кроме того, `break` внутри такого макроса выйдет
из внутреннего `do`, поэтому скрывать управление внешним циклом в макросе —
плохая идея. В обычном коде по-прежнему используйте фигурные скобки у `if`.

## Условная компиляция и заголовки

`#if` выбирает, какой код попадёт в компиляцию:

```c
#ifndef DEBUG
#define DEBUG 0
#endif

#if DEBUG
#define TRACE_INT(x) PRINT_INT(x)
#else
#define TRACE_INT(x) ((void)0)
#endif
```

При `DEBUG == 0` вызов `TRACE_INT(count)` заменяется пустым действием.
`(void)0` означает вычислить ноль и явно отбросить его значение. Это
выражение ничего не меняет и подходит на место инструкции при добавлении `;`.
Аргумент не вычисляется, поэтому **не помещайте полезную работу в отладочный
макрос**: `TRACE_INT(count++)` меняет поведение программы между сборками.
По той же причине не пишут `assert(ReadData())`: при определённом `NDEBUG`
стандартный `assert` не вычисляет аргумент.

`assert` из `<assert.h>` предназначен для проверки предположений программы:
при ложном условии он сообщает об ошибке и прерывает выполнение.
В сборке с `NDEBUG` эти проверки отключаются. Поэтому чтение данных,
выделение памяти и другие необходимые действия выполняются независимо
от диагностических проверок.

`#ifdef DEBUG` проверяет **наличие определения**, а не его значение.
При `#define DEBUG 0` условие `#ifdef DEBUG` истинно, а `#if DEBUG` — ложно.
Неизвестное имя в выражении `#if` считается нулём. Переменные C, `sizeof`
и значения `enum` препроцессору недоступны.

Сохраните исходник `macros.c` из ссылки выше в текущую папку.
Включить режим при сборке можно без редактирования файла:

```sh
cc -std=c17 -DDEBUG=1 macros.c -o macros && ./macros
```

Для MSVC аналог — `/DDEBUG=1`.

Защита заголовка от повторного включения — ещё одно применение макросов:

```c
#ifndef NSU_POINT_H_INCLUDED
#define NSU_POINT_H_INCLUDED

typedef struct TPoint {
    int x;
    int y;
} TPoint;

#endif
```

При втором включении в ту же единицу трансляции имя уже определено,
и содержимое пропускается. Эта защита не устраняет множественные определения
глобальных объектов в разных `.c`: для них всё ещё нужны правильные
объявления `extern` и одно определение.

## `##` и два уровня раскрытия

Оператор `##` склеивает два токена в один:

```c
#define FIELD(name) field_##name

int FIELD(count) = 5; // int field_count = 5;
```

Результат должен быть допустимым токеном. Это не операция над строками
во время выполнения.

У `#` и `##` есть тонкость: непосредственно участвующий аргумент
не раскрывается заранее. Если нужно сначала раскрыть макрос, добавляют слой:

```c
#define VERSION 3
#define STRINGIZE_RAW(x) #x
#define STRINGIZE(x) STRINGIZE_RAW(x)

// STRINGIZE_RAW(VERSION) -> "VERSION"
// STRINGIZE(VERSION)     -> "3"

#define JOIN_RAW(a, b) a##b
#define JOIN(a, b) JOIN_RAW(a, b)

int JOIN(version_, VERSION) = 3; // int version_3 = 3;
```

В `STRINGIZE_RAW(VERSION)` параметр находится непосредственно после `#`,
поэтому сразу становится строкой `"VERSION"`. В `STRINGIZE(VERSION)`
внешний макрос не применяет к параметру ни `#`, ни `##`: аргумент сначала
раскрывается в `3`. Затем вызов `STRINGIZE_RAW(3)` получает уже этот текст
и превращает его в `"3"`.

Аналогично, прямой `JOIN_RAW(version_, VERSION)` дал бы имя
`version_VERSION`. Вызов через `JOIN` сначала раскрывает `VERSION`,
затем склеивает токены `version_` и `3`, получая `version_3`.
Два уровня нужны из-за конкретного порядка раскрытия, а не из-за
особого поведения слова `VERSION`.

Это полезно для генерации имён и диагностических строк. В повседневном коде
обычно достаточно понимать приём, а не строить из него отдельный язык.

## Как увидеть раскрытый код

Для GCC / Clang:

```sh
cc -std=c17 -E -P examples/macros.c -o /tmp/macros-expanded.c
```

`-E` останавливает обработку после препроцессора, `-P` убирает служебные
указания строк. Файл будет большим из-за `<stdio.h>` — ищите `int main`.
Для MSVC можно использовать `cl /nologo /TC /std:c17 /EP examples/macros.c`.

При ошибке в макросе сначала выпишите подстановку. Проверьте скобки,
число вычислений каждого аргумента и итоговую структуру `if` / `else`.
Так ошибку обычно видно быстрее, чем по сообщению компилятора.

## Дополнительные примеры с объяснениями

### 1. Одних скобок мало?

```c
#define NEXT(x) x + 1
int result = 2 * NEXT(3);
```

Каков результат? Исправьте определение.

Получится `2 * 3 + 1`, то есть 7. Нужно `#define NEXT(x) ((x) + 1)`:
тогда результат 8. В исправленной версии аргумент используется один раз.

### 2. Сколько раз вызывается функция?

```c
#define MAX(a, b) (((a) > (b)) ? (a) : (b))
int result = MAX(ReadValue(), 0);
```

Пусть первый вызов `ReadValue()` возвращает 5, второй — −2.
Каким станет `result`? Что изменится с функцией `MaxInt`?

Макрос вызовет `ReadValue()` дважды: сравнит 5 с 0, затем вернёт −2
из выбранной ветви. Функция `MaxInt(ReadValue(), 0)` прочитает одно
значение 5 и вернёт 5. Похожая запись не означает одинаковое поведение.

### 3. Нулевой режим

```c
#define DEBUG 0
#ifdef DEBUG
    puts("A");
#endif
#if DEBUG
    puts("B");
#endif
```

Какие вызовы останутся после препроцессора, если фрагмент находится внутри `main`?

Только `puts("A")`: имя `DEBUG` определено, но его значение равно нулю.
