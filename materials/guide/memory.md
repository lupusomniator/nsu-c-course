# Динамическая память

{% include course-context.html %}

У массива `int values[100]` вместимость выбрана при написании программы.
Иногда количество элементов становится известно только во время работы.
**Динамическое выделение памяти** позволяет запросить нужное число байтов
и освободить их, когда данные больше не нужны.

## Выделить, использовать, освободить

```c
{% include_relative examples/memory.c %}
```

При успешном выделении вывод:

```text
0 1 4 9
```

В примере `count` равно четырём, чтобы результат был легко виден. Тот же
запрос памяти можно сделать для размера, полученного при выполнении;
проверки размера от этого не становятся менее важными.

`malloc` из `<stdlib.h>` получает число байтов. Выражение
`count * sizeof(*values)` означает «число элементов × размер элемента».
Здесь `sizeof` узнаёт размер `int`, не читая объект через `values`.

`malloc` возвращает указатель на выделенную область или `NULL` при неудаче.
Тип результата — `void*`, общий указатель на объект без указанного типа данных.
В C он может неявно преобразовываться в `int*`; приведение перед `malloc` не нужно.
Правильное объявление функции из `<stdlib.h>` нужно обязательно.

## Память изначально не содержит готовых значений

Выделенная `malloc` память не инициализирована. Первый цикл записывает
числа, и только после этого второй цикл их читает.

Запись `(int)(i * i)` явно преобразует значение в `int`. Здесь `i` принимает
значения от 0 до 3, поэтому квадрат точно помещается. При произвольном большом
`count` пришлось бы отдельно проверять диапазон самих вычисляемых значений.

`free(values)` освобождает область. После него обращаться к элементам нельзя.
Сам вызов `free` не обнуляет переменную-указатель. Присваивание `values = NULL`
может помочь не использовать её повторно, но не исправляет другие копии адреса.

Важно освобождать именно адрес, полученный от функции выделения памяти,
а не адрес одного из внутренних элементов. Повторное освобождение той же
области недопустимо. `free(NULL)` разрешён и ничего не делает.

## Проверка размера

Перед умножением в примере проверяется `count > SIZE_MAX / sizeof(*values)`.
`SIZE_MAX` из `<stdint.h>` — максимальное значение `size_t`.
Если произведение не помещается, оно могло бы превратиться в другое,
меньшее число. Тогда памяти было бы выделено меньше, чем ожидает программа.

Нулевое число элементов обработано отдельно: программа сразу завершается.
Это позволяет не зависеть от особенностей `malloc(0)`.

Даже представимый размер не гарантирует успеха: свободной памяти может
не хватить. Поэтому `NULL` проверяется независимо от проверки умножения.

## Кто отвечает за освобождение

Указатель сам по себе не сообщает, нужно ли его освобождать.
Адрес локального массива, адрес внутри чужой области и результат `malloc`
могут иметь одинаковый тип `int*`, но разную роль.

Полезно договориться о **владельце**: это часть программы, которая отвечает
за освобождение. Например, функция создаёт массив и передаёт ответственность
вызывающему коду, а функция суммы только временно читает его.
Такую договорённость записывают в описании функции.

Если адрес потерян до `free`, память остаётся занятой без возможности
использования — это **утечка**. Если обратиться после `free`, получится
доступ к уже освобождённой памяти. Оба случая особенно заметны в долгоживущих программах.

## Изменение размера

`realloc` может изменить размер выделенной области. Для ненулевого нового
размера безопаснее сначала сохранять результат во временный указатель:

```c
int* resized = realloc(values, newCount * sizeof(*values));
if (resized != NULL) {
    values = resized;
    count = newCount;
}
```

Этот фрагмент предполагает, что `newCount > 0` и умножение заранее проверено.
При неудаче исходная область остаётся действительной, поэтому старый адрес
нельзя терять. При успехе нужно пользоваться новым указателем: прежний
и указатели на элементы прежней области больше нельзя использовать.
Добавленная часть памяти не инициализируется автоматически.

## Как замечать ошибки

На поддерживаемых GCC/Clang сборка с AddressSanitizer помогает обнаруживать
выходы за границы и использование освобождённой памяти:

```sh
cc -std=c17 -Wall -Wextra -g -fsanitize=address,undefined memory.c -o memory && ./memory
```

Проверяется только выполненный путь программы. Успешный запуск не заменяет
понимание того, кто владеет памятью и сколько элементов доступно.


## Растущий массив: свяжем размер, вместимость и владение

Теперь размер действительно будет меняться при выполнении. Пусть программа
добавляет числа по одному и заранее не знает их итоговое количество.
Хранить нужно три связанных значения: адрес памяти, число заполненных
элементов и вместимость. Соберём их в структуру.

```c
{% include_relative examples/dynamicBuffer.c %}
```

Вывод при успешном выделении памяти:

```text
size=1 capacity=2
size=2 capacity=2
size=3 capacity=4
size=4 capacity=4
size=5 capacity=8
data: 10 20 30 40 50
```

У структуры есть договорённость: `size <= capacity`; первые `size` элементов
инициализированы; память для `capacity` элементов принадлежит этому буферу.
Начальное `{0}` задаёт `data == NULL`, `size == 0`, `capacity == 0`.
Это корректный пустой буфер, а не массив из нуля автоматически созданных элементов.

Проследим добавление числа 30. Перед вызовом `size == 2`, `capacity == 2`,
в памяти лежат 10 и 20. Места для третьего числа нет. Функция выбирает новую
вместимость 4, проверяет размер и просит `realloc` расширить область.
Только после успеха она заменяет адрес и вместимость, записывает 30
в элемент с индексом 2 и увеличивает `size` до 3.

Почему `size` увеличивается последним? Если память получить не удалось,
число ещё не добавлено. В таком случае функция возвращает 0 и оставляет
прежний буфер целиком действительным. Вызывающий код может освободить его
или решить, что делать дальше. Если сначала увеличить `size`, состояние
будет обещать существование ещё не записанного элемента.

При добавлении 40 выделение вообще не выполняется: место уже есть.
Удвоение вместимости — выбранная стратегия роста, а не правило `realloc`.
Две проверки защищают разные действия: первая — вычисление новой вместимости,
вторая — перевод числа элементов в число байтов.

Если до расширения кто-то сохранил `int* first = buffer.data`, после
успешного `realloc` этот указатель использовать нельзя. Область могла
переехать; даже совпадение численного адреса не даёт права продолжать
использовать старое значение указателя. Новые адреса элементов получают
от обновлённого `buffer.data`.

## Три способа разместить массив

Динамическое выделение — один из способов получить память. Сравним его
с массивом фиксированной вместимости и массивом переменной длины.

## Когда размер становится известен при выполнении

Пусть количество элементов передаётся в функцию:

```c
void PrintLast(int n) {
    if (n <= 0 || n > 100) {
        return;
    }

    int values[n]; // VLA: variable-length array.
    for (int i = 0; i < n; ++i) {
        values[i] = i + 1;
    }
    printf("%d\n", values[n - 1]);
}
```

`PrintLast(3)` создаёт массив из трёх элементов и выводит 3,
`PrintLast(5)` — массив из пяти элементов и выводит 5.
Размер вычисляется при прохождении объявления. Для каждого созданного
массива он затем остаётся прежним: изменение `n` не меняет длину уже
существующего массива.

Такой массив называется **VLA**, массивом переменной длины. Его время жизни
начинается при выполнении объявления и заканчивается при выходе из области
видимости. В типичной реализации место берётся из стека, но стандарт
не требует именно этого способа размещения.

Компилятор не добавляет универсальную безопасную границу `n`, а конец
слишком большого массива не становится особой «недоступной частью».
Если ресурсов не хватит, программа может аварийно завершиться; переносимого
результата `NULL`, как у `malloc`, у такого объявления нет. Поэтому проверка
`n <= 100` в примере — наше решение об ограничении размера.
`PrintLast(1000000000)` вернётся ещё до объявления массива благодаря этой проверке.

См. [документацию GCC о VLA](https://gcc.gnu.org/onlinedocs/gcc/Variable-Length.html).

Размер должен быть положительным; слишком большой размер опасен для стека.
Здесь мы ограничили его сотней элементов. В C17 нельзя написать
`int values[n] = {0};` для VLA: элементы нужно заполнить отдельно.

**Поддержка VLA в C17 необязательна.** GCC и Clang их поддерживают,
а MSVC — нет. Поэтому отказ MSVC от `int values[n]` не означает,
что все компиляторы C обязаны отвергать такой код.
См. [режимы стандартов MSVC](https://learn.microsoft.com/en-us/cpp/build/reference/std-specify-language-standard-version).
Запускаемый пример для GCC / Clang: [variableArray.c]({{ '/materials/examples/variableArray.c' | relative_url }}).

## Почему нельзя `static int values[n]`

Теперь объединим две идеи:

```c
// Ошибка в C17: массив переменной длины со статическим временем хранения.
void Remember(int n) {
    static int values[n];
}
```

У обычного VLA есть конкретное выполнение объявления, в котором берётся
текущее `n`, создаётся массив нужной длины, а затем этот массив прекращает
существовать при выходе из блока.

У локального `static` другая модель: **один объект на всё выполнение программы**.
Его размер не выбирается заново при каждом вызове. Представим вызовы:

```c
Remember(3);
Remember(100);
```

Какая длина должна быть у единственного массива — 3 или 100? Нужно ли менять
её при втором вызове? Что тогда делать с сохранёнными элементами и ранее
полученными указателями? Можно придумать разные правила, но C не задаёт
ни "выбрать длину при первом вызове", ни "перевыделять при каждом вызове"
для локального `static`.

Правило C17 прямо запрещает объекту VLA иметь статическое время хранения.
Для такого массива нужен размер, заданный **целочисленным константным
выражением**. Это ограничение языка, согласованное с моделью хранения,
а не неспособность компьютера в принципе выделить память во время выполнения.

Размер можно задать числом, элементом `enum` или подходящим макросом:

```c
enum { CAPACITY = 100 };

void Remember(void) {
    static int values[CAPACITY]; // Разрешено: один массив из 100 элементов.
    ++values[0];
    printf("%d\n", values[0]);
}
```

Первый вызов выводит 1, второй — 2. Размер определён независимо от вызовов,
а содержимое сохраняется между ними.

### Почему `const int` не помогает

```c
void Work(void) {
    const int n = 10;
    static int values[n]; // Не является переносимым объявлением в C17.
}
```

Человеку видно, что `n` равно 10 и его нельзя изменять. Однако в C17 `const`
означает запрет изменения объекта через это имя, а не превращение имени
в целочисленное константное выражение. Способность оптимизатора вычислить
значение заранее не меняет этого правила языка.

Для переносимого кода замените `const int n = 10;` на
`enum { N = 10 };`, а размер — на `N`. Макрос `#define N 10` также подходит:
после препроцессора в объявлении будет число 10.
Некоторые компиляторы принимают вариант с `const` как расширение;
это не делает его переносимым C17. Не переносите сюда правила C++.

Та же проблема возникает вне функций:

```c
int n = 10;
int values[n]; // Ошибка: такой массив нельзя объявить на уровне файла.
```

Объект `values` здесь и без слова `static` имел бы статическое время хранения.
Кроме того, вариативно модифицированные типы не допускаются в области файла.

## Что выбрать вместо запрещённого объявления

Если есть небольшая известная верхняя граница, разделите **вместимость**
и **число используемых элементов**:

```c
enum { CAPACITY = 100 };

void Process(int n) {
    if (n <= 0 || n > CAPACITY) {
        return;
    }

    int values[CAPACITY];
    for (int i = 0; i < n; ++i) {
        values[i] = i + 1;
    }
    printf("%d\n", values[n - 1]);
}
```

Место есть для 100 элементов, но функция использует только первые `n`.
Остальные элементы не инициализированы, и читать их здесь не нужно.
Такой код работает и без поддержки VLA. `static` добавляйте только тогда,
когда нужен один общий массив с сохранением содержимого между вызовами.

Если размер произвольный или данные должны пережить вызов, обычно памятью
управляют явно через `malloc` и `free` либо передают в функцию готовый буфер
и его вместимость. При динамическом выделении нужно проверять размер,
успех выделения и заранее договориться, кто освобождает память.
Мы уже реализовали такую договорённость в `TIntBuffer`: объект структуры
находится в `main`, но его поле `data` указывает на отдельно выделенную область.
Выход из блока структуры сам по себе не вызывает `free`.

## Сопоставление объявлений

Внутри функции `int a[5]` — автоматический массив фиксированного размера.
`int b[n]` — VLA, если `n` не является целочисленным константным выражением.
`static int c[n]` недопустим в переносимом C17. `static int d[size]` также
недопустим, если `size` — объект `const int`. Вариант с
`enum { LIMIT = 5 }; static int e[LIMIT];` допустим: размер константный,
а время хранения статическое. Фиксированный размер и длительное хранение
описывают разные свойства.

После выбора хранения вернёмся к исходному тексту: разберём препроцессор,
включая макросы с параметрами, составные действия и генерацию имён.
